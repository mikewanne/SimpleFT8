# P153 V1 — SWR-Freeze: Minimum über stabiles Fenster statt Snapshot

## Trigger (Mike-Field-Bug 28.05.2026)

Bandwechsel 15m → gesperrt. Manueller TUNE: Tuner matchte sichtbar auf
SWR 2,5 (Anzeige zeigte es), ABER das System fror >4,0 ein → Band blieb
gesperrt („SWR 4.0 > Limit 3.0"). 2. TUNE: zufällig 2,3 eingefroren →
Band frei.

**Mike-Diagnose (bestätigt durch Code):** Der Freeze nimmt einen EINZIGEN
Momentan-Snapshot. Wenn dieser Moment einen Mess-/Regel-Ausreißer (4,0)
erwischt obwohl der Tuner stabil bei 2,5 ist → falscher Wert eingefroren.

**Auslöser-Verkettung:**
- P142 (27.05.) zog den Freeze von „nach Phase B" auf „nach Phase A".
  Vorher hatte der SWR 5s Phase-B-Zeit zum Stabilisieren → Snapshot traf
  ruhigen Moment. Jetzt direkt nach Match → SWR-Stream noch am Schwanken
  → Snapshot fragil.
- P148 (27.05.) machte es sichtbar (Anzeige hält letzten echten Wert statt
  auf 1,0 zu springen).
- Derselbe Snapshot-Mechanismus erklärt auch frühere false-1,0-Vorfälle.

**Pattern-Klasse Hardware-Sicherheit, 4. Iteration** (P53/P76-A/P142/P153).

## Mike-Spec (final, 28.05.)

> „bei 10 sekunden 7-9 sekunde davon" + Aggregat: **median**

- Während der TUNE-Dauer SWR-Werte mit Zeitstempel sammeln
- Am Ende: aus dem Fenster **[Dauer-3s, Dauer-1s]** (= Sek. 7-9 bei 10s
  Tune) den **Median** nehmen
- Allerletzte Sekunde (Dauer-1 bis Dauer) ausgeschlossen — Übergangs-Spikes
  vor tune_off vermeiden
- Fallback: keine Samples im Fenster → alter Snapshot `radio.last_swr`
- Median (statt Min): einzelner 4,0-Ausreißer kippt ihn nicht, bei echter
  Oszillation bleibt er ehrlich (Mike-Entscheidung 28.05., Sicherheit)

## Aktuelle Lage im Code

`ui/mw_tx.py:_tune_start` (Z. 161): Phase A ist **passives Warten** —
`QTimer.singleShot(duration_s*1000, _tune_stop)`. Es werden KEINE
SWR-Werte gesammelt.

`ui/mw_tx.py:_tune_stop` (Z. 268): Freeze = `self.radio.last_swr`
(einziger Momentan-Snapshot, der Bug).

`ui/mw_tx.py:_on_meter_update` (Z. 917-931, P148): SWR-Branch aktualisiert
Anzeige während TX/TUNE. **Hier** kommen die SWR-Ticks an — idealer Sammel-
Punkt (analog `_fwdpwr_samples` Z. 906).

`flexradio.py:1460`: `_last_swr` + `meter_update.emit("SWR", swr)` nutzen
denselben Wert — Anzeige und Snapshot sind wertgleich, divergieren nur
durch Timing.

### 3. Neuer Helper `_compute_match_swr()` — Min über Fenster

```python
import statistics

def _compute_match_swr(self) -> float:
    """P153: SWR-Match-Wert = Median über stabiles Fenster
    [Dauer-3s, Dauer-1s]. Fallback radio.last_swr wenn leer.

    Mike-Spec 28.05.: einzelner Snapshot erwischte Ausreißer.
    Fenster schließt initialen Abfall (Tuner sucht) UND die
    Übergangs-Sekunde vor tune_off aus. Median statt Min — robust
    gegen Ausreißer in beide Richtungen.
    """
    dur = getattr(self, '_tune_duration_s', 0)
    samples = getattr(self, '_tune_swr_samples', [])
    win_start = max(0.0, dur - 3.0)
    win_end = dur - 1.0
    window = [swr for el, swr in samples if win_start <= el <= win_end]
    if window:
        return statistics.median(window)
    # Fallback: alter Snapshot
    return self.radio.last_swr
```

## Sicherheits-Überlegung (Median gewählt)

Mike hat nach Abwägung **Median** gewählt (28.05.). Robuster als Min:
- Fenster schließt die instabile Match-Suchphase (Sek. 0-7) aus
- In Sek. 7-9 ist der Tuner fertig → Werte stabil
- Median kippt nicht bei einem einzelnen 4,0-Ausreißer (= Mike's Bug)
- Bei echter Oszillation (grenzwertige Antenne) bleibt Median ehrlich
  → keine zu optimistische Freigabe (Hardware-Sicherheit)

**Frage an DeepSeek:** Median über Fenster sauber? Edge-Cases?

## Cancel-Fall (Mike-Bonus-Beobachtung)

Mike: „stabiler Wert 2,3, dann abbrechen → nimmt 2,3 nicht". Bei Cancel
während Phase B setzt P142 `_tune_last_valid_swr = None` (Z. 251,
Sicherheit). Das ist by-design — soll im Scope bleiben oder separat?
**V1-Entscheidung:** im Scope lassen (P142-Hardware-Schutz). Nur
