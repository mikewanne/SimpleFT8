# P104 — V2 Self-Review

## Code-Verifikation V1-Findings

**F1 (BESTÄTIGT)** — `power_watts` wird nur in `mw_qso.py:580` für
ADIF-Log gelesen. `_current_power_watts` in ControlPanel ist die richtige
Source-of-Truth zur QSO-Schreibzeit (wird bei jedem Power-Preset-Klick
gesetzt — Z.1972, Z.1983).

→ Fix sauber: `tx_power=self.control_panel._current_power_watts or 10`
(Default-Fallback falls None vor erstem QSO).

**F2 (KORREKTUR)** — `tx_level_bar` im ControlPanel ist `setVisible(False)`
(Z.917). User kann TX-Audio-Pegel NIRGENDS sehen oder ändern außer im
Settings-Dialog. Mike-Argument greift: bleibt eh auf 100% (gecappt 75%),
niemand ändert es manuell.

→ Setting kann komplett raus. `tx_level_bar` + `tx_level_label` bleiben
für internen Status (kein Dead-Code-Risiko, intern referenziert).

**F3 (NEU)** — `Settings.power_watts` Property in `config/settings.py:224-225`
ist explizite Property (nicht via _data-Dict). Bei Setting-Pop in `load()`
würde der Property-Zugriff `self._data["power_watts"]` einen `KeyError`
werfen. → Property muss MIT raus, ODER `_data["power_watts"]` darf nicht
gelöscht werden.

**Lösung:** Property raus, `mw_qso.py:580` direkt auf `_current_power_watts`.

**F4 (ORANGE)** — Tests in `test_settings_dialog_smoke.py:62-63` haben
eigene Mock-Settings-Klasse mit `power_watts`-Property. Bei Refactor
müssen die Tests angepasst werden (Property raus).

**F5 (NEU)** — Mike-Wunsch „rotes Band = nicht klickbar" hat
UX-Konflikt: bei DEAKTIVIERTEM QPushButton greift `setStyleSheet`
trotzdem aber Qt überlagert oft mit Default-Grau. Lösung: Buttons
bleiben aktiv (setEnabled(True)), aber `_on_band_clicked(band)` prüft
zuerst ob Daten vorhanden → wenn nicht: silent no-op (kein Dialog,
kein Tooltip — User sieht ja schon visuell rot).

Alternative: rote Buttons disabled mit explizitem `QPushButton:disabled`-
Style. Aber Qt-disabled Buttons sind nicht zuverlässig schön stylebar
auf macOS. → **Variante 1: aktiv mit no-op-Klick** ist sauberer.

**F6 (NEU)** — Band-Reihenfolge: für Funker ist absteigende Wellenlänge
(160m → 10m) untypisch. Standard ist aufsteigende Frequenz (160m, 80m,
60m, 40m, 30m, 20m, 17m, 15m, 12m, 10m) — von tief nach hoch wie auf
einem Funkgerät-Display. Andere Stellen im Projekt nutzen welche Reihenfolge?

→ `config/settings.py` hat `BAND_ORDER`? Lass mich checken (Schritt 0
unvollständig). Wenn ja, nutze ich die. Wenn nein: feste Liste in V3
gemäß Klassik (160m-10m absteigend Wellenlänge / aufsteigend Freq).

**F7 (NEU)** — Test-Mocking: `_refresh_rf_status` baut Buttons
dynamisch. Tests müssen sicherstellen dass:
- Jeder Band-Button korrekt grün/rot ist nach `store.get_all(...)`
- Klick auf grüner Button öffnet Dialog (Mock + assert)
- Confirm → `store.clear_band` called
- TX-Lock disabled alle Buttons

**F8 (GELB)** — Migrationspfad: alte `power_watts`/`tx_level` aus
config.json beim ersten Start nach Update entfernen via Pop in
`load()` (analog P52, P80). Tests verifizieren idempotent.

**F9 (NEU — DIRT)** — `_reset_to_defaults` (Settings-Dialog) ruft
`self.power.setValue(...)` + `self.tx_level.setValue(...)`. Wenn die
Widgets gelöscht sind, muss `_reset_to_defaults` angepasst werden.

**F10 (ORANGE)** — `tx_level_bar` und `tx_level_label` im ControlPanel
zeigen aktuell den TX-Audio-Pegel. Wenn Setting weg + fester Wert 75%,
zeigt die Bar dann „75%" konstant. Das ist OK aber Mike könnte sich
fragen wofür diese internen Anzeigen wenn unverändert. → V3-Diskussion:
ggf. komplett verstecken oder eigener Dead-Code-Sweep separat.

### `_current_power_watts`-Zugriff aus mw_qso

Direkter Zugriff `self.control_panel._current_power_watts` ist hässlich
(private-Attribut). Sauberer: Property/Getter `current_power_watts()`
in ControlPanel als public API. Aber: KISS-Klausel — wenn nur einmal
gelesen, direkter Zugriff ist OK (war auch bei `_current_scoring_mode`
in P103 so).

→ Direkter Zugriff mit `getattr(self.control_panel, '_current_power_watts', 10)`
für Defensive.
