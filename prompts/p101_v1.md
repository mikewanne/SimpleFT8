## Bug A — Rechtsklick-TUNE startet das Tunen nicht direkt

**Symptom:**
- App offen, Radio AN, TUNE-Button sichtbar (tuner_present=true).
- User macht Rechtsklick auf TUNE → Menü mit „TUNE 10s / 15s / 20s" erscheint.
- User wählt z.B. „TUNE 15s".
- **Erwartet:** TUNE-Button wird visuell aktiv (grün), Hardware geht in TUNE-Modus mit 10 W auf ANT1 für 15 s.
- **Tatsächlich:** **Nichts passiert.** Kein Tune startet, Button bleibt visuell inaktiv.
- Workaround: User macht danach Linksklick auf TUNE → tunt ABER mit dem Default-Setting `tune_duration_s` (z.B. 15 s), NICHT mit dem rechts gewählten Wert. → Mike will explizit Single-Click-Override „in einem Rutsch".

**Code-Pfad heute (v0.97.72):**

1. `ui/control_panel.py:1015-1018` (`_RadioCard._on_tune_button_context_menu`):
   ```python
   for sec in (10, 15, 20):
       act = menu.addAction(f"TUNE {sec}s")
       act.triggered.connect(
           lambda checked=False, s=sec: self.tune_override_requested.emit(s))
   menu.exec(self.btn_tune.mapToGlobal(pos))
   ```

2. `ui/control_panel.py:1428-1429` (`ControlPanel.__init__`): bubblen
   ```python
   radio_card.tune_override_requested.connect(
       self.tune_override_requested.emit)
   ```

3. `ui/main_window.py:763-764`: final wire
   ```python
   self.control_panel.tune_override_requested.connect(
       self._on_tune_override)
   ```

4. `ui/mw_tx.py:106-125` (`_on_tune_override`):
   ```python
   if not self.radio.ip: return
   if duration_s not in (10, 15, 20): return
   if self.btn_tune.isChecked():
       self.btn_tune.setChecked(False)
       self._tune_stop(None)
       return
   self.btn_tune.setChecked(True)
   self._tune_start(duration_s)
   ```

**Mögliche Ursachen (zu klären in V2+R1):**

- **U1** – Signal-Bubbling-Bricht durch fehlende Connection-Garantie. `radio_card.tune_override_requested` ist ein Klassen-Attribut; in der `_RadioCard`-Instance wird es vom Python-Descriptor-Protokoll instanziert. Wenn Connection zur Instanz-Zeit (vor `_RadioCard.__init__` fertig) gemacht wird, sollte sie greifen. Wahrscheinlichkeit: niedrig.

- **U2** – `act.triggered` Lambda-Closure bug: `lambda checked=False, s=sec: ...` ist Standard-Capture-Trick gegen Late-Binding. Sollte stabil sein. Wahrscheinlichkeit: niedrig.

- **U3** – `menu.exec()` blocking: Während `menu.exec()` im modalen Sub-Eventloop läuft, kommt das `triggered`-Signal aber wird NACH `exec()` returned. Dann emittet `tune_override_requested` und alle nachfolgenden Signals laufen synchron in derselben Stack-Frame. Beim `setChecked(True)`+`_tune_start(15)` wird `_tune_start` synchron aufgerufen → setzt `_tune_active=True` + `radio.tune_on()`. Sollte funktionieren. Wahrscheinlichkeit: niedrig — aber Mike sieht null Effekt.

- **U4** – `btn_tune.isChecked()` ist nach einem vorherigen unsauber beendeten TUNE noch True (Auto-Stop-Token-Race) → `_on_tune_override` nimmt den „läuft → stop"-Pfad. Wahrscheinlichkeit: MITTEL.

- **U5** – TUNE-State-Mismatch zwischen App-Restart und Code-Pfad: `tuner_present` wurde gerade umgeschaltet. Möglicherweise hat `_tune_in_progress` oder `_tune_active` einen Init-Bug nach dem `set_tuner_present(True)`-Refresh. Wahrscheinlichkeit: niedrig.

- **U6** – `radio.tune_on()` wird gerufen, aber das FlexRadio ignoriert es weil die Radio-Frequenz noch nicht auf der Tune-Freq sitzt (Sync-Race). `_tune_start` setzt `set_frequency` VOR `set_tx_antenna` und `tune_on`. Race auf das FlexRadio-API möglich. Wahrscheinlichkeit: niedrig — Linksklick hat dasselbe Pattern und funktioniert.

- **U7** – **Print-Debug pflanzen**: Vor der Code-Analyse braucht es Live-Beweis welcher Pfad genommen wird. `print("[P101] _on_tune_override called", duration_s, "isChecked=", self.btn_tune.isChecked())` an Pfad-Anfang + nach `_tune_start`-Call. **Erste Aktion.**

**Fix-Strategie (KISS, V3-Phase):**

Variante A: **Diagnose-Print + Verifikation**, dann erst Code ändern. Wahrscheinlichkeit hoch dass es **U4** ist (`isChecked()` hängend von Auto-Stop-Race).

Variante B: `_on_tune_override` IMMER stoppen wenn `_tune_active==True` (statt nur `btn_tune.isChecked()` zu prüfen) und danach NICHT return, sondern weiter zum Start-Pfad. Falls Mike zweites Rechtsklick will, soll es als „Switch-Dauer" funktionieren statt „Stop". → **Mike-Wunsch nochmal klären**: 2. Rechtsklick = Stop oder Switch?

Variante C: `_on_tune_override` ohne `isChecked()`-Check — IMMER `_tune_stop(None)` rufen (idempotent: macht nichts wenn `_tune_active=False`), dann mit kurzer Verzögerung (QTimer.singleShot(50ms)) den neuen `_tune_start(duration_s)` zünden. Damit ist die Auto-Stop-Race entkoppelt.

**Variante A ist V2-Pflicht.** Erst messen, dann fixen.

## Bug B — QMenu-Padding-Asymmetrie (Häkchen klebt am Rand)

**Symptom (Mike sagt):**
> wir haben bei beiden auswahlboxen [QSO-Spalten + RX-Spalten] **links zuviel padding** und auf der **rechten seite wo die OKAY haken sind gar kein padding** [Häkchen klebt am rechten Rand].

**Analyse Heute (P100 v0.97.72):**
- QSO-Panel `_build_columns_menu()` (qso_panel.py): `padding: 4px 32px 4px 28px`. KEIN `QMenu::indicator`-Eintrag → Qt Default-Indicator (das Häkchen-Symbol) wird gerendert. Position: links im padding-left-Bereich.
- RX-Panel beide Stylesheets: `padding: 4px 32px 4px 28px` + `QMenu::indicator { width: 14px; height: 14px; }`. Indicator-Position: links.

**Mike sagt aber „Häkchen rechts klebt am Rand"** → das wäre ein RECHTS-Indicator. Qt's Default-Indicator-Position für `QMenu::item` ist **links**. Möglich dass Mike die `:checked`-Text-Farbe (Color-Change ohne Symbol) als „Haken" interpretiert? In dem Fall ist links Text-Start = padding-left-Ende. Wenn padding-left=28 und Indicator-Width=14, dann ist Text bei x=14+ kleiner Spacing. Text sieht „weit links" aus.

**Realistischer:** Mike's „links zuviel" bezieht sich darauf dass das **Indicator-Symbol** dort `links` Platz braucht (28px) der visuell als leerer Block links wirkt, **dann der Text**, **dann zu wenig Platz rechts** zwischen Text-Ende und Border. Das ist asymmetrisch:
```
| [□ Indikator]  Text....... |
  ^28px         ^Text       ^32px (aktuell)
```

WAIT — Mike sagt rechts ist KEIN Padding. Wenn padding-right=32 ist, sollte rechts viel Platz sein. Hmm.

**Hypothese**: Qt rendert padding-right ANDERS als erwartet wenn `:checked` ein Häkchen rechts vom Text setzt (theme-abhängig). Oder Mike sieht ein anderes Theme-Verhalten.

**Sichere Fix-Strategie (Variante A):**

1. **Explizit Indicator stylen** in beiden Menüs:
   ```css
   QMenu::item { padding: 4px 24px 4px 36px; }
   QMenu::indicator {
       width: 14px;
       height: 14px;
       margin-left: 8px;    /* schiebt Indicator vom linken Border weg */
   }
   ```
   - padding-left 36px = 8px (margin-left) + 14px (indicator) + 14px (Lücke zum Text)
   - padding-right 24px = symmetrischer Platz nach Text-Ende
   - Indicator hat 8px Luft zum linken Rand statt 0

2. **TUNE-Override-Menü** (`_on_tune_button_context_menu` in control_panel.py:1010-1014): aktuell `padding: 4px 20px 4px 20px` ohne Indicator. Mike hat hier nichts beklagt — bleibt vermutlich symmetrisch ok. **Nicht ändern.**

3. **Test**: visuelle Korrektheit ist subjektiv → kein Pytest-Assert, nur Stylesheet-Verifikation dass die Werte gesetzt sind.
